Results of the drills run on 2026-11-13 against the local converge
([../../deploy/local-converge.md](../../deploy/local-converge.md)): 3 edge, 2 core and 1 backup
Debian 13 systemd node on one host with 16 GB of memory, the three edge nodes in three simulated
locations joined by a router with `tc netem` delays (about 3 ms between two of them, 23 ms to the
third). The recovery drills on the production environment (node loss, database leader loss,
point-in-time restore, rolling deploy) are in [2026-11-13-azure.md](2026-11-13-azure.md).
Times are UTC.

## Tooling

- `tests/drills/drillctl`: setup (24 tenants, 40 sites, 24 OTLP tokens through the console
  API), `load` with a ledger of every acknowledged event, `verify` (every 202 looked up by
  path in Umami, OTLP sums in `api.metrics_minute`), `lag`, `probe` (dashboard gap on both
  core nodes), `commits` (acknowledged-commit writer), `snapshot` and `checksum` (table
  checksums at time T under write locks), `clock` (NATS `/varz` time and HTTP `Date`).
- Load client: one Go process on the host. Web events solve the real proof; a connection
  failure moves to the next edge address (what a browser does with several A records); the
  tracker never resends an answered event. OTLP exports retry connection errors and 429,
  502, 503, 504 up to 6 times. A DNS stand-in checks port 80 every 30 s and answers the
  healthy addresses.
- Drill scripts: `tests/drills/{edge-loss,nats-member,db-leader,core-outage,partition,nats-restart,pitr,cert-renewal,clock-skew,rolling-deploy}.sh`,
  load profile `tests/load/run.sh` with `tests/load/profiles.env` (web 50/s and API 116/s at
  the expected peak, factor 10 for the burst).

## Load at 10 times the expected peak

Run A, 02:18 to 02:23 UTC, against the bounds gateway p99 under 250 ms, collector p99 under
500 ms, no acknowledged event lost, and the backlog drained within 600 s:

| Measure | Result |
|---|---|
| Web events | 149,995 sent, 149,995 acknowledged, gateway p99 126 ms |
| OTLP exports | 347,988 acknowledged, collector p99 81 ms |
| Acknowledged and lost | 0 web events, 0 exports |
| Duplicate rows | 11, from a replayer restart during the drain (below) |
| Backlog empty | **1,101 s** after the run, above the 600 s bound |

The edge answered every request within its bounds; the consumers set the drain time. Measured
drain rates while the backlog was worked off:

1. First configuration: web about 77/s, OTLP about 150/s. The replayer's 16 lanes each spend
   several confirmed NATS round trips per event (duplicate guard, visit state, acknowledgement).
   The metrics writer confirmed its 256 acknowledgements one after another, each a round trip
   to a consumer leader that can sit in another location (150 a second means about 6.7 ms
   each).
2. Changes: `REPLAYER_WORKERS` 16 to 128 and `REPLAYER_MAX_IN_FLIGHT` 512 to 900 (core role
   defaults); the metrics writer sends its acknowledgements 64 at a time after the batch commits
   (`internal/metricswriter/writer.go`).
3. After the change: OTLP about 1,417/s, above the 1,160/s load. Web about 280/s, with Umami's
   single Node process at about 65% of a core: at 10 times the web load (500/s) one Umami
   process is the limit. That led to several Umami processes per node, measured in the next
   section.

The 11 duplicate rows come from restarting the replayer during the drain to apply the new
settings. The replayer records each sent event after Umami's 200 and then acknowledges it, so a
restart between Umami's 200 and that record stores the event twice; this is the replayer's
at-least-once window (`internal/replayer/replayer.go`).

A second run (run B) is not reported: the shared test host was saturated during it (load
average 624 to 880), so its numbers measure the host, not the design.

## Web drain with several Umami processes

Follow-up, 05:09 to 05:14 UTC. Each core node runs `core_umami_processes` Umami processes on
the one database with one `APP_SECRET` (`roles/core/templates/compose.yml.j2`: `umami` plus
`umami-2` to `umami-N`). `UMAMI_URL` of the replayer lists all of them, and the replayer sends
each visitor to `Umami[visitorHash % N]` with the same fnv-1a hash that picks the visitor's lane,
so a visitor's events go to one process, one at a time, in stream order. Why the choice of
process does not change sessions or visits: [../umami-contract.md](../umami-contract.md) item 14.

Measurement: `TestDrainRateByUmamiProcesses` (`internal/replayer`,
`REPLAYER_DRAIN_MEASURE=<events>`), on one NATS server, one postgres:18.6 container and N Umami
3.5.0 containers each capped at **one core** (`NanoCPUs`), with one replayer in the test process
using the core role's 128 lanes and 900 in flight. A backlog of 12,000 page views (2,000
visitors, 6 each) is published first, then the replayer starts and the time until the stream is
empty is taken; every run checks that Umami holds exactly 12,000 views. Each process is warmed
with 600 events first. The host load average was 3 to 5.

| Umami processes | Run 1 (cold) | Run 2 (warmed) | Run 3 (warmed, 6,000 events) | CPU per Umami process (cores, run 2) |
|---|---|---|---|---|
| 1 | 454/s | 502/s | 442/s | 1.00 |
| 2 | 665/s | 755/s | 681/s | 0.85, 0.99 |
| 3 | 842/s | 927/s | | 0.77, 0.74, 0.99 |
| 4 | | 1,162/s | | 0.75, 0.71, 0.78, 0.99 |

Sends split evenly (6,000 events over 2 processes: 3,018 and 2,982). In each run one process
sat at the one-core cap while the others stayed below it. The drain ends only when the slowest
process's visitors are done, so that process sets the rate.

Reading: scaling is 1.5 times for 2 processes, 1.85 times for 3 and 2.3 times for 4. Each idle
process holds about 115 MB. One process here (about 450 to 500/s on a full core) is faster than
in run A (280/s at 65% of a core), where every event paid cross-location NATS round trips on a
saturated host, so these numbers are an upper bound for one process. Applied to run A's 280/s,
2 processes drain about 420/s. Production nodes have two vCPUs and run 2 processes, one per vCPU
(`core_umami_processes` in `infra/ansible/roles/core/defaults/main.yml`); the effect on the
availability targets is in [../availability.md](../availability.md).

## Restart after power-off

`tests/drills/start-unit.sh` runs one Debian 13 systemd node from `infra/local`, converged with
the base role and the edge role's `start_unit.yml` (shared word for word with the core role
apart from the project directory). It runs a test-only compose project in `/opt/veristar/edge`
with the pinned NATS and etcd images and the edge project's restart policy. A power-off is
`docker kill` of the node container (no shutdown), followed by `docker start`.

| Step | What | Measured (05:39 to 05:47 UTC) | Verdict |
|---|---|---|---|
| 1 | power-off and power-on | `nats`, `etcd`, `slow`, `client` all running again; unit `Result=success`, started in the same second Docker became active | pass |
| 2 | `nats` and `client` set to restart policy `no` (Docker leaves them down at boot), power-off | the unit started `nats` at once and `client` 100 s later, once `slow` (healthy only 100 s after start, like Umami's 120 s start period on core) was healthy; all running, `Result=success` | pass |
| 3 | control: unit disabled, same as step 2 | `nats` and `client` stay `exited`, so step 2 measured the unit, not Docker | pass |

The unit first ran with systemd's 90 s default timeout for a oneshot. `docker compose start`
waits for each dependency's health condition before it starts a dependent, so on a core node
(the replayer, control plane and jobs wait for Umami's health, 120 s start period) systemd
stopped it. A run with `START_UNIT_TIMEOUT=90s` at 05:24 to 05:32 showed `start operation timed
out. Terminating.` at 90 s, `Result=timeout`, `client` left `exited`. Both units now set
`TimeoutStartSec=15min`.

On the local converge only, Docker attached the node container's two networks in the other
order in one of three boots (`eth0` became the private address). The base role's firewall names
interfaces, so SSH to the node then timed out; the drill disables the unit over `docker exec` for
that reason. Cloud servers keep their interface names across reboots.

## Fixes made from the drills

- Edge and core roles install `sa-{edge,core}-start.service`, which runs `docker compose start`
  after Docker comes up. In the edge node loss drill, edge 2's NATS container stayed
  `Exited (255)` after power-on, because the restart policy does not retry a start that fails
  during daemon startup. The unit is verified in "Restart after power-off" above.
- `deploy/images/go-service.Dockerfile` copies `docs/compliance` and `docs/reference/openapi`,
  which the platformctl and jobs images embed.
- `bootstrap.yml` runs on the current Patroni leader (it ran on the first core node, which is a
  replica after a failover).
- Core compose: the pgBackRest server container is created after PostgreSQL (two containers
  creating one new volume raced). The repository's `tls-server-auth` uses one line per client
  CN (the value after `=` lists stanzas).
- Replayer and metrics writer throughput, from the load run (above).
