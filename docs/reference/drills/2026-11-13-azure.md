### NATS route liveness: root cause and fix (2026-11-14)

**Root cause.** Not the stream: `WEB_EVENTS` (R3) had its leader on node 1 and node 3 current
the whole time, so the stream had quorum. Node 1's gateway was not connected to node 1's NATS
server: the services listed all three servers in `NATS_URL`, nats.go picks one at random, and
that gateway (and node 1's collector and replayer) had picked node 2's. A powered-off peer sends
no FIN or RST, so the client noticed only by missed pings: nats.go's defaults are one ping every
2 minutes with 2 outstanding. Node 1's gateway logged `nats disconnected ... stale connection`
and reconnected to node 3 at 03:30:15, 5.5 minutes after the power-off; until then every publish
waited the 2 s `PublishAckWait` and failed (503). The routes between servers had the same blind
spot at the default 2 minute ping (the stale route closes at 03:25:51 to 03:25:55).

**Fix** (commits 590864b and 82110a2):

- Ansible: on a converged node every service lists only its own node's server
  (`edge_nats_urls` is `tls://nats:4222`, `core_nats_urls` the node's own private address). That
  server goes away only with its node, whose health then takes the node out of DNS. Single-tier
  layouts keep the full list, starting at a different server per core index.
- Ansible: routes ping every 5 s with 3 outstanding (`edge_nats_route_ping_interval`,
  `edge_nats_route_ping_max`, `templates/nats.conf.j2`); applied by a config reload
  (`Reloaded: cluster`).
- Code: every client pings every 5 s with 3 outstanding and keeps the configured server order
  (`internal/natsx/conn.go`). This ships with the next release; production runs v0.1.0 with the
  Ansible part, which removes the failure on its own (scenario 4 below).

**Proof before production**: three `nats:2.15.3-alpine`
servers with JetStream and an R3 stream, a publisher at 4 a second for 330 s, one server frozen
with `docker pause` for 180 s (no FIN or RST, as a powered-off VM). The full local converge with
the three-node layout was started for this, but with another build on the controller it left
under 1 GB free and the host's load average above 270, so it was taken down to protect the host's

## Rollout incident: web.veristar.app 502 on node 3 (2026-11-14)

What was seen: `https://web.veristar.app/` answered 502 from `production-node-3`; the other two
nodes answered 200. Times are UTC.

| Step | Finding |
|---|---|
| Trigger | the accelerated networking change (`infra/tofu/modules/node`, applied to the three NICs one at a time) deallocates and starts each VM. While node 3 was off, the leader kept writing and recycled the WAL node 3 still needed |
| Replica | node 3's Patroni member started, then stayed in recovery with `requested WAL segment 0000000200000004000000DB has already been removed` and `waiting for WAL to become available at 4/DB002000`; its `restore_command` was empty, so it could not fetch the segment from the pgBackRest repository that holds it |
| HAProxy | at boot the start unit (`sa-core-start`) waits for the compose project; HAProxy had `depends_on: postgres: condition: service_healthy`, so it never started on a node whose own member is not healthy, and exited `255`. Umami and the web site reach the database through the local HAProxy, so the node's web route answered 502 even though the leader on node 2 was healthy |
| Recovery | node 3 reinitialised from the leader through the Patroni REST API (`POST /reinitialize`), `docker compose start haproxy`; web answered 200 from node 3 at 16:17:06 |
| Fix 1 (`cf49d75`) | `postgresql.recovery_conf.restore_command: pgbackrest --stanza=sa archive-get %f "%p"`: a replica that falls behind the leader's WAL retention now fetches the missing segments from the repository |
| Fix 2 (`050d3de`) | HAProxy depends on `postgres: service_started`. It routes to the leader on any node through the Patroni checks, so it never needed the local member to be healthy |

### Planned switchover could not find its candidate

The v0.2.0 rollout stopped twice at `Wait until this node is a replica` on the leader
(`production-node-2`), with `production-node-3` streaming as synchronous standby at lag 0. The
leader's Patroni log showed the cause:

```
WARNING: Request failed to production-node-3: GET https://10.10.3.13:8008/patroni (... TLSV13_ALERT_CERTIFICATE_REQUIRED ...)
INFO: Member production-node-3 is not reachable
WARNING: switchover: no healthy members found, switchover is not possible
```

The REST API requires a client certificate (`verify_client: required`), and Patroni presents one
on its requests to other members only from the `ctl` section (`patroni/request.py` reads
`ctl.certfile` and `ctl.keyfile`, never the `restapi` files). `patroni.yml` had no `ctl`
section, so every member's health check of another failed. `patronictl switchover` fell back to
the failover key in the DCS, and the leader refused it. No planned switchover had run on this cluster
before: the task runs only when the postgres-ha image changes, and v0.2.0 is the first release
after v0.1.0. The failover of the leader loss drill above does not need the check, because a
member that cannot reach the others still takes part in the leader race. Fix (`b22c797`): a `ctl` section with the node certificate, key and CA. Applied on the
three nodes by SIGHUP before the rollout resumed; a request with the node's Patroni
configuration then returned 200 from both other members.
