### Second run under event load (2026-11-14)

`production-node-2` was powered off the same way at 03:24:46 and started at 03:29:49, while a
client on the controller (`.scratch/scratch/drills/evload`, built on `tests/gateway/gwclient`)
sent 4 page views a second to the probe site through `https://in.veristar.app` for 14 minutes
with real DNS and HTTP keep-alive, solving a new challenge every 20 events, and wrote a ledger of
every answer. Afterwards every acknowledged path was looked up in Umami's `website_event`.

| Measure | Result |
|---|---|
| Events sent | 3,108: 2,284 answered 202, 803 answered 503, 26 client errors (timeouts and a reset connection) |
| **Acknowledged events lost** | **0**: all 2,284 acknowledged paths are in Umami; one event answered with a client timeout is stored too |
| `in` answer | node 1 left it 32 s and node 2 44 s after the power-off; from 44 s to 335 s only node 3 was in the answer; node 1 came back 32 s after node 2's start |
| `app` | node 2 left the answer 99.2 s after the power-off; 0 of 313 requests failed |
| Node 2 healthy again | 62.6 s after the start, every container running without a hand start (the observability start-at-boot unit of the first run's fix) |

The 503s all came from `production-node-1`, the leader of the `WEB_EVENTS` stream, which the
keep-alive client stayed connected to: from 03:24:52 to 03:29:19 its gateway logged
`event not queued ... context deadline exceeded` (16, 27, 221, 238, 236 and 85 per minute) and
its NATS health failed, so Traffic Manager took it out of `in`; node 3's gateway queued every
event it got. Node 1's NATS closed the route connections to the lost node one by one: the first
on the 10 s write deadline at 03:25:19, the next as stale connections at 03:25:51 to 03:25:55;
publishing recovered at 03:29:19, before node 2 was back. So one lost node left one surviving
node unable to queue for about 4.5 minutes while the other served alone. Clients that resolve
again moved to node 3 (the per-request client of the same run saw 2 failures in 313); a
client holding a connection to node 1 got 503 for that time. Under investigation: NATS route
liveness on a powered-off peer (route `ping_interval` and the pooled route connections), not
changed yet.

### Gateway load on one node

Not run. The profile of `make gateway-load` (2,500 events a second for 30 s, target p99 under
50 ms, [../gateway-limits.md](../gateway-limits.md)) sends from one machine with a different
client address per event, straight to the gateway container. A production node takes events
only through Caddy, which sets the client address from the TCP peer, and the gateway's
production limits are 20 events a second per site and /24 per node and 200 per site per node.
From one outside machine with the one probe site, at most 20 events a second can be accepted
by a node; 2,500 a second would need at least 125 sites from one address, or a temporary limit
change on the node. Neither was done: creating test sites needs a console session, and the
limits are not changed without the operator. The CI agent's numbers on 2-vCPU runners (2,400 and
2,221 events a second, p99 174 ms and 222 ms, gateway and NATS sharing two cores) are the
closest measurement to a `Standard_B2as_v2` node, which runs everything else on the same two
vCPUs.
