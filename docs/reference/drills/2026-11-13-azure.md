## Database leader loss (readiness 3.2, 3.3)

`.scratch/scratch/drills/db-failover.sh` (kept outside the repository, it holds the node
addresses): the leader `production-node-2` was powered off with
`az vm stop --skip-shutdown` at 18:52:12. A probe on `production-node-1` asked HAProxy for
`pg_is_in_recovery()` once a second; the dashboard health `/core` of the two surviving nodes was
read once a second.

| Measure | Result |
|---|---|
| Writes through HAProxy | unavailable from the power-off until **30.3 s** after it; `production-node-3` became leader on timeline 2 |
| Committed rows | the newest `cp.audit_log` row from before the power-off (id 1) was present on the new leader |
| `/core` on the surviving nodes | 503 from 2.5 s to 30.3 s after the power-off (33 of 68 checks), 308 before and after |
| Rejoin | `az vm start` returned after 13 s; the old leader streamed again as a replica with lag 0 **64 s** after the start |
| Containers after the power-on | every container running except Alertmanager, which Docker left at exit code 255 from the boot; started by hand. Fix: the observability project got the same start-at-boot unit as the edge and core projects (`sa-observability-start.service`) |

Traffic Manager kept the surviving nodes in `app` and `web`: the dashboard health failed for
about 28 s, less than the three failed 30 s probes that remove an endpoint.

## Node loss (readiness 3.1)

`.scratch/scratch/drills/node-loss.sh`: `production-node-1` (then the synchronous standby)
was powered off with `az vm stop --skip-shutdown` at 18:56:38, kept off for 300 s and started
again. DNS was read through `1.1.1.1` every 2 s (Traffic Manager's own name servers do not
answer on port 53 from the controller's network); one HTTPS request a second to
`https://in.veristar.app/v/1.2.0/sdk.js` and to `https://app.veristar.app/` went through the
controller's normal resolver.

| Measure | Result |
|---|---|
| `in` answer without the node | **41.9 s** after the power-off |
| `app` answer without the node | **93.2 s** after the power-off |
| Requests to `in` | 698 from the power-off to 120 s after recovery, 5 failed (0.72 %): curl timeouts at 57.8, 243.6, 375.9, 432.1 and 494.7 s with no connection made. One identical timeout also happened 8 s **before** the power-off, so part of these come from the controller's network and resolver |
| Requests to `app` | 698, none failed |
| Back in the answers | `in` 61.3 s and `app` 98.3 s after the start |
| Node healthy again | `/` and `/core` 308 and every container running 233.4 s after the start, after Alertmanager was started by hand at 223 s (same exit code 255 as above) |

**Not measured: acknowledged event loss.** Counting acknowledged events needs a site to send
them to, and every site belongs to a tenant that an operator creates after signing in to the
console with GitHub. Nobody has signed in to production yet (see "Waiting" below).
