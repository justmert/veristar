### NATS route liveness: root cause and fix (2026-11-14)

**Root cause.** Not the stream: `WEB_EVENTS` (R3) had its leader on node 1 and node 3 current
the whole time, so the stream had quorum. Node 1's gateway was not connected to node 1's NATS
server: the services listed all three servers in `NATS_URL`, nats.go picks one at random, and
that gateway (and node 1's collector and replayer) had picked node 2's. A powered-off peer sends
no FIN or RST, so the client noticed only by missed pings: nats.go's defaults are one ping every
2 minutes with 2 outstanding. Node 1's gateway logged `nats disconnected ... stale connection`
and reconnected to node 3 at 03:30:15, 5.5 minutes after the power-off; until then every publish
waited the 2 s `PublishAckWait` and failed (503). The routes between servers had the same blind
spot at the default 2 minute ping (the stale route closes at 03:25:51 to 03:25:55).

**Fix** (commits 590864b and 82110a2):

- Ansible: on a converged node every service lists only its own node's server
  (`edge_nats_urls` is `tls://nats:4222`, `core_nats_urls` the node's own private address). That
  server goes away only with its node, whose health then takes the node out of DNS. Single-tier
  layouts keep the full list, starting at a different server per core index.
- Ansible: routes ping every 5 s with 3 outstanding (`edge_nats_route_ping_interval`,
  `edge_nats_route_ping_max`, `templates/nats.conf.j2`); applied by a config reload
  (`Reloaded: cluster`).
- Code: every client pings every 5 s with 3 outstanding and keeps the configured server order
  (`internal/natsx/conn.go`). This ships with the next release; production runs v0.1.0 with the
  Ansible part, which removes the failure on its own (scenario 4 below).

**Proof before production** (`.scratch/scratch/drills/natsliveness`): three `nats:2.15.3-alpine`
servers with JetStream and an R3 stream, a publisher at 4 a second for 330 s, one server frozen
with `docker pause` for 180 s (no FIN or RST, as a powered-off VM). The full local converge with
the three-node layout was started for this, but with another build on the controller it left

### Gateway load on one node (2026-11-14)

`production-node-2` (then a Patroni replica) was taken out of all four Traffic Manager profiles
(`az network traffic-manager endpoint update --endpoint-status Disabled` for `in-2`, `otlp-2`,
`app-2`, `web-2`); at 05:30:35 no profile answered its address. Its gateway limits were raised
through the same path Ansible uses (`deploy.yml --limit production-node-2,localhost` with
`edge_gateway_env` passed as extra vars: `RATE_SITE_*` and `RATE_PREFIX_*` 10,000 a second, burst
20,000, everything else unchanged). k6 2.3.0 ran on an operator workstation, with `hosts` mapping
`in.veristar.app` to the node, the probe site, proofs solved beforehand
(`.scratch/scratch/drills/proofgen`, each used at most 50 times) and a desktop Chrome user agent:
the profile of `make gateway-load` through the node's Caddy instead of straight at the gateway
container. The workstation is 58 ms from Denmark East, so the node-side latency is taken from the node's
Caddy access log (`duration` of every `/v1/e` request in the run's window); the client figures
include the round trip. A short-lived VM next to the node, which would have measured without the
round trip, was not created: the permission system refused the VM creation.

| Offered rate | Achieved | Answered 202 | Node-side p50 / p95 / p99 | Client p99 | Node CPU |
|---|---|---|---|---|---|
| 2,500/s for 30 s | **863/s** (48,665 iterations dropped, k6 at its 1,000 VU cap) | 26,315 of 26,336 (21 answered 403) | 379 / 1,695 / **2,134 ms** | 3.15 s | 0 % idle during the run; Caddy 76 to 90 % of a core, gateway 47 to 50 % |
| 1,200/s for 30 s | 1,173/s | all 35,393 | 39 / 141 / 198 ms | 404 ms | |
| 800/s for 30 s | 795/s | all 23,927 | 7.8 / 66 / 92 ms | 237 ms | |
| 500/s for 30 s | 499/s | all 15,001 | 4.0 / 29 / **51.4 ms** | 177 ms | |

Memory was not the limit: after the 2,500/s run the node had 5,624 MiB available of 7,943 MiB.

**Result: the target (2,500 events a second with p99 under 50 ms on one instance,
[../gateway-limits.md](../gateway-limits.md)) is not met on a `Standard_B2as_v2` converged node.**
The node reaches the 50 ms p99 at about 500 events a second and saturates its two vCPUs, mostly
in Caddy's TLS and HTTP work, near 1,200 a second. For the expected peak of the availability
statement (50 web events a second, 500 in the 10x burst) one node is enough and three share the
load. The smallest size that meets the target was not measured (no short-lived VM, above); no
size is named from estimates. After the runs the limits were restored with the same
`deploy.yml --limit` run without the extra vars: the gateway's settings on node 2 hash the same as
on node 1, `make production-plan` shows `No changes.`, the four endpoints were enabled again and
every profile answers all three addresses.

### Gateway load on one node

Not run. The profile of `make gateway-load` (2,500 events a second for 30 s, target p99 under
50 ms, [../gateway-limits.md](../gateway-limits.md)) sends from one machine with a different
client address per event, straight to the gateway container. A production node takes events
only through Caddy, which sets the client address from the TCP peer, and the gateway's
production limits are 20 events a second per site and /24 per node and 200 per site per node.
From one outside machine with the one probe site, at most 20 events a second can be accepted
by a node; 2,500 a second would need at least 125 sites from one address, or a temporary limit
change on the node. Neither was done: creating test sites needs a console session, and the
limits are not changed without the operator. The CI agent's numbers on 2-vCPU runners (2,400 and
