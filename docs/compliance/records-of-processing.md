---
title: "Records of processing"
description: "The records of processing activities for the service."
---

Two records of processing: the hosting operator as processor for tenants (GDPR
Art. 30(2)) and the hosting operator as controller of console accounts (Art.
30(1)). The hosting operator is the party that runs the service and hosts its
data (`terms.md` section 1). SCF does not run the service; it receives project
statistics on each tenant's instruction (`terms.md` section 1.1). This page is
not legal advice. Last updated 2026-11-17.

## A. Processing on behalf of tenants (hosting operator as processor)

| Item | Entry |
|---|---|
| Processor | the hosting operator, named in the repository |
| Controllers | each enrolled tenant, as listed in `cp.tenants` |
| Categories of processing | collection of web page views and custom events through the tracker; country lookup; network classification of each event for fraud detection (access, organisation, hosting, anonymiser or unknown, from the address in memory), reduced to per-site daily counts and an integrity grade; per-site daily counts of the page signals tracker 1.3.0 reports (framed page views, pages left without being visible) for the same grade; per-site daily counts of the requests for the tracker file and of those carrying Global Privacy Control, attributed to the site by the page origin in the `Referer` header, to estimate the visits that are not measured; daily visitor token computation; queueing; storage and reporting in Umami; daily aggregates for the operator view and for the project statistics SCF receives; signed usage reports the tenant creates from those aggregates, and their public links; collection of HTTP server metrics and spans from tenant applications, classification of each request as application, preflight, health check or uptime probe traffic (from its method, route and user agent), reduction to request counts and latency histograms, storage and reporting; reading the public ledger records of the Stellar accounts and contracts the tenant declares, reduced to three counts per id and UTC day and one count of weekly active accounts per ISO week; erasure on request |
| Categories of data subjects | visitors of tenant websites; clients of tenant APIs (only as anonymous request counts and latencies); Stellar accounts that initiate operations involving the tenant's declared accounts and contracts (only as keyed hashes during an open week, then a count) |
| Categories of personal data | for web visitors, held in memory only: IP address and user agent, and the autonomous system of the address. Stored: daily visitor token as part of Umami's session id, browser, operating system, device type, screen size and language (sent by tracker releases before 1.3.0 only), country, page path with allowlisted query, referrer scheme and host, page title (from tracker 1.3.0 only when the site asks for it), event names and event data; per site and day, events per network class and the distinct networks as keys under a daily secret that is destroyed at midnight, deleted after four days. The `Referer` and `Sec-GPC` headers of a request for the tracker file are read in memory for the request and never stored; only per-site daily counts remain. For API clients: none at the level of a person. The user agent of a request (`user_agent.original`, or the legacy `http.user_agent`) and its `user_agent.synthetic.type` are read in memory by the collector to set the traffic class and never stored; stored are tenant, service, normalized route, method, status, traffic class and latency buckets. For on-chain activity: while an ISO week is open, a random 32-byte key for the week and the HMAC-SHA256 under that key of every account that initiated an operation involving one of the tenant's verified ids; the key and the hashes are deleted when the week closes, and only the count of distinct accounts remains. No account address of a counterparty is stored |
| Recipients | the tenant's members (its own dashboards, and the AI clients they connect through the MCP server, `privacy-strategy.md` section 10); anyone the tenant gives the link of a signed usage report, which holds aggregates only (`privacy-strategy.md` section 12); SCF, which receives the project statistics of `terms.md` section 1.1 on the tenant's instruction: the per site and day web aggregates, the integrity grade with the counts it is computed from, the tracker file and Global Privacy Control counts, the page signal counts, the hourly and daily API aggregates, the daily on-chain counts and the weekly active accounts (`dpa-template.md` clause 3); sub-processors in `subprocessors.md` |
| Transfers to third countries | none for analytics data (`data-residency.md`) |
| Retention | `privacy-strategy.md` section 4 |
| Security measures | `dpia.md` section 5 |

## B. Console accounts (hosting operator as controller)

| Item | Entry |
|---|---|
| Controller | the hosting operator |
| Purpose | sign-in to the console, membership of projects, audit of changes |
| Data subjects | tenant staff and operators who sign in, and the people operator admins add to the operator roster |
| Personal data | for a GitHub sign-in: numeric GitHub user id and GitHub login. For a wallet sign-in: the Stellar account address (the public key) whose key signed the sign-in challenge; it is personal data once it is linked to the person's console account. For a passkey sign-in: the passkey's credential id, its public key and the address of the soropass smart account that key controls (a Stellar contract address derived from the two); no biometric data, which never leaves the person's device. For all: project memberships and roles, the cohort a member proposed for a project and the user id of the member who created or revoked a usage report or set a cohort, session token hashes, MCP credential hashes with their names and last use, audit log entries naming the user id (MCP tool calls included, without their answers). For operators: the roster row of each operator identity (GitHub id and login, or Stellar address), its role, status and status reason, its enrollment window and the user id of the admin who added it; the passkeys an operator adds for the operator area's step-up (credential id, public key, name, creation and last use); the time of the last step-up, held in the session; audit rows of roster changes and passkey registrations, which keep the login or address, the reason and the passkey name |
| Recipients | GitHub, Inc. for a GitHub sign-in (`subprocessors.md`). A wallet sign-in has no recipient: the wallet extension runs in the person's own browser, and the challenge it signs never reaches the Stellar network. A passkey sign-in has no recipient: the passkey answers in the person's own browser and device, and the console contacts no Stellar network service for it |
| Transfers | a GitHub sign-in passes through GitHub in the United States; a wallet sign-in and a passkey sign-in pass through no third party |
| Retention | sessions: 7 days absolute, 24 hours idle; accounts: until the person deletes the account or the service stops; operator roster rows: until an operator admin removes them or the person deletes the account; operator passkeys: until the person removes one, an admin resets them, a removal leaves the person with no active roster row, or the person deletes the account; the audit log: while the service runs |
| Erasure | each person deletes their own account on the console's Account page; GitHub id, login, Stellar address, passkey (credential id, public key and account address), operator roster rows and operator passkeys, memberships, sessions, MCP credentials and invites are deleted (refused with `last_operator_admin` while the person is the last active operator admin), and audit rows keep a pseudonymous account id (`erasure.md` section 7). Unlinking a sign-in method removes that identity from the account at once |
